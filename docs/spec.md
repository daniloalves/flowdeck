# MVP Specification — Claude Code Agent Orchestrator

Oct 22, 2026 · Danilo Herrera Alves · English translation. Provisional name "Regente", built as **FlowDeck**.
Design changes adopted before implementation are listed in `docs/DESIGN-REVIEW.md`; where they
differ from this document, the review wins.

## Vision and goals

A Linux desktop app that shows several Claude Code sessions on an infinite canvas, each one bound
to an account, with real-time status, visible usage, agent-to-agent communication and full
restoration after a reboot.

The MVP is done when these five criteria pass:

1. Open 6 Claude Code sessions on 2 different accounts, on the same canvas, at the same time.
2. Know in under 1 second, looking at the canvas, which session is working, which finished and
   which is waiting for action, with a system notification in the last two cases.
3. See on each node the account in use and that account's usage for the 5-hour and 7-day windows.
4. Connect two nodes on the canvas and have one agent send a task to the other, with the send
   recorded in a log.
5. Reboot the computer and, when opening the app, get back the same layout, each node on the
   right account and in the right conversation.

Principles: everything local, no telemetry, auditable code; the app never stores or reads
credentials, it only points at each account's config directory.

## Scope

The MVP covers a single local workspace with Claude Code terminals and plain shells.

| In the MVP | Later |
| --- | --- |
| Infinite canvas with terminal nodes (drag, resize, zoom, pan) | Notes, freehand drawing, browser portals |
| One terminal per node, running inside a tmux session | Multiple workspaces and "floors" with isolated branches |
| Account per node via `CLAUDE_CONFIG_DIR`, with a visible badge | Remote workspaces over SSH or Docker |
| Per-node status via Claude Code hooks + system notification | Automatic summary of what each agent did |
| Usage per account (5 h and 7 days) read from local files | Exhaustion forecast and historical charts |
| Connections between nodes + local MCP server for agent messages | Reusable roles with custom instructions |
| Save and restore layout and sessions after reboot | Cross-machine sync, mobile app |
| Linux x64 (Ubuntu/Debian), AppImage package | macOS, Windows, arm64 |

## Architecture

The app never runs Claude directly: it creates tmux sessions, shows each one in a node and reacts
to the events Claude Code itself emits. Usage is read from the JSONL files in each account
directory; restoration depends only on SQLite and the session ids.

## Tech stack

| Layer | Choice | Why |
| --- | --- | --- |
| Desktop shell | Electron + electron-vite | Mature; node-pty works without friction |
| UI | React + TypeScript + Zustand | Simple, serialisable canvas state |

| Notifications | Electron Notification API (libnotify) | Native on GNOME/KDE |
| Tests | Vitest (unit) + Playwright for Electron (E2E) | |
| Packaging | electron-builder → AppImage and .deb | |

## Data model

SQLite at `~/.local/share/flowdeck/flowdeck.db`. Canvas state is the source of truth for
restoration. Tables: `account`, `node`, `edge`, `node_status`, `message` (see
`packages/app/src/main/db/migrations.ts` for the authoritative schema). Account usage is not
persisted: it is recalculated every 30 s and kept in memory.

## Components

Six modules in the main process; the UI only renders state and sends commands through IPC.

1. **Session manager (tmux)** — each node is a tmux session on the dedicated socket. The app
   creates the session and then only attaches through the PTY, so closing the app kills nothing.
   The socket's tmux config is generated by the app: status bar off, `remain-on-exit on` to
   detect process death, 50,000 lines of history.
2. **Accounts** — an account is just a config directory. The accounts panel lists the `~/.claude*`
   directories found, lets the user name them and pick a colour, and opens `claude` with the
   account's directory for the first login. The app never reads `.credentials.json`; it only
   checks whether the file exists to show "logged in / not logged in".
3. **Events and status (hooks)** — every hook calls the same script, which forwards the JSON
   received on stdin together with the node id to the app's socket.

   | Claude Code event | Node state | App action |
   | --- | --- | --- |
   | `SessionStart` | idle | Store `session_id` in `node.claude_session_id` |
   | `UserPromptSubmit` | working | Animated border |
   | `Stop` | idle | Green border + "finished" notification if the app is not focused; deliver queued messages |
   | `Notification` | needs_input | Orange border + notification with the event text |
   | `SessionEnd` or dead pane | dead | Grey node with a "resume" button |

   The script always exits 0 with a 1 s timeout, so it never blocks Claude if the app is closed.
4. **Usage per account** — every 30 s the app reads the JSONL files under `<config_dir>/projects/**`,
   sums input and output tokens of messages inside the 5 h and 7 day windows and shows them on the
   account badge, as absolute tokens and as a percentage of a cap configured per account.
5. **Agent communication (MCP)** — a stdio MCP server (`flowdeck-mcp`) knows which node is calling
   and talks to the app through the same socket.
   - `list_peers()` returns the nodes connected to this one by edges, with title, account and state.
   - `send_to(peer, message)` only works if an edge exists between the two nodes; it is stored in
     `message` and returns "queued" or "delivered".
   - `read_inbox()` returns received messages not yet read.

   Delivery: if the target is `idle`, the app types the message into its terminal followed by Enter,
   prefixed with `[from: <node title>]`. If it is `working` or `needs_input`, the message waits for
   the next `Stop`. The app never types over a busy agent.
6. **Restore** — on start the app loads the canvas from SQLite and, for each node, runs
   `tmux has-session`. If the session exists, it just attaches. If not (there was a reboot), it
   recreates the session with `claude --resume <claude_session_id>`. An optional `.desktop` file in
   `~/.config/autostart` opens the app at login.

## Security

The biggest risk is not a leak through the app, but one agent instructing another; that is why
communication only exists where the user drew an edge.

- **Network:** the app makes no outbound requests and has no dependency with telemetry.
- **Event socket:** Unix socket at `$XDG_RUNTIME_DIR/flowdeck.sock` with mode 0600. No TCP port.
- **Credentials:** the app never opens `.credentials.json` nor reads variables holding tokens.
- **Agent messages:** only between nodes joined by an edge, limited to 4,000 characters, all
  logged with sender, target and time. A received message is prefixed with its origin, so the
  agent knows it did not come from the user.
- **Dangerous permissions:** nodes with `--dangerously-skip-permissions` get a red border, and the
  app refuses to create an edge into them from a node that is not in that mode, preventing
  escalation through prompt injection.
- **Electron:** `contextIsolation` on, `nodeIntegration` off in the renderer, strict CSP, no remote
  content loaded.

## Implementation phases

1. **Foundation** — monorepo, Electron + React + React Flow, SQLite schema and migrations, typed IPC.
   Acceptance: the app opens, creates an empty node, drags it, closes and reopens with the node in the same place.
2. **Persistent terminals** — tmux with a dedicated socket, node-pty, xterm.js in the node, synced resize.
   Acceptance: run `htop` in a node, close the app, reopen and `htop` is still there; `tmux -L flowdeck ls` lists the session.
3. **Accounts** — discovery of `~/.claude*`, accounts panel, Claude node with a chosen account, coloured badge.
   Acceptance: two nodes on different accounts; `/status` inside each shows the right e-mail.
4. **Status and notifications** — hook script, socket server, state machine, borders and notifications.
   Acceptance: ask for a long task, switch windows and get notified when it ends; a permission request turns the node orange.
5. **Restore** — store `session_id`, rebuild at start, optional autostart.
   Acceptance: reboot with 4 nodes on 2 accounts; on opening, all come back in the right conversation.
6. **Usage** — JSONL reading, 5 h and 7 day windows, configurable cap, accounts panel.
   Acceptance: displayed tokens match `ccusage` for the same window within 5 %.
7. **Agents talking** — edges, `flowdeck-mcp`, queue and delivery, log, security rules.
   Acceptance: a "leader" node sends a task to a busy "reviewer"; the message only arrives after the reviewer's `Stop` and appears in the log.

## Risks

| Risk | Impact | Mitigation |
| --- | --- | --- |
| JSONL or hook format changes in a Claude Code update | Usage or status stops working | Parsers isolated in `usage/` and `events/` with fixture tests; status falls back to "unknown" instead of hanging |
| Many xterm.js instances weigh on the canvas | Slowness with 10+ nodes | DOM renderer; future: render only visible nodes |
| Typed input collides with something the user is typing | Garbled text | Deliver only on `idle` and only when the node is not focused; otherwise queue |
| Several accounts seen as working around limits | Issue with Anthropic's terms | No automatic account rotation; the account is an explicit per-node choice |
